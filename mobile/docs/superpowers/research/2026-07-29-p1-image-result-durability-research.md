# Research dossier - durable tool-generated images

Date: 2026-07-29  
Subsystem: TALOS mobile tool loop / chat persistence / Vault

## Local diagnosis

- `generate_image` returns a typed `images` payload after the binary has been
  saved in the Vault.
- `runTalosAgentLoop` already knows how to place that payload on a following
  user turn so a vision-capable model can inspect the generated image.
- the controller reduces every tool result to `{ ok, content }`, dropping the
  image before it reaches that loop;
- the generated Vault grant is immediately revoked by the generic
  Library-only save helper, so no durable message attachment can be created;
- the final completion contract has no generated-attachment field, and the
  chat store therefore persists only assistant text;
- the renderer already displays persisted image attachments correctly, so a
  second image store or base64-in-message format would duplicate established
  behavior and bloat encrypted chat rows.

## Current primary sources

1. OpenRouter, **Image Generation**, inspected 2026-07-29:
   <https://openrouter.ai/docs/guides/overview/multimodal/image-generation>
   - the dedicated Image API returns generated bytes as `data[].b64_json`;
   - the declared `media_type` is present when the result is not the default
     raster PNG;
   - model discovery and generation are separate typed endpoints.
2. OpenRouter, **Image Inputs**, inspected 2026-07-29:
   <https://openrouter.ai/docs/guides/overview/multimodal/image-understanding>
   - private/local image input is carried as base64 in a multipart chat
     message;
   - text should precede the image blocks;
   - accepted image count is provider/model dependent.
3. Google, **Gemini API image generation**, inspected 2026-07-29:
   <https://ai.google.dev/gemini-api/docs/image-generation>
   - generated image output is base64 data with a MIME type;
   - Gemini supports conversational text-and-image generation and subsequent
     image processing;
   - interleaved output must be handled as typed parts rather than flattened
     into text.

Exact upstream pins:

- OpenRouter Image API and image-input contracts retrieved 2026-07-29;
- Gemini Interactions image-generation contract last updated 2026-07-16 and
  retrieved 2026-07-29;
- conformance remains pinned by repository tests; no runtime SDK is added.

## Upstream decision

**Adapt the official byte/part contracts behind TALOS-owned result,
persistence, and authority adapters.**

- preserve provider image bytes as the existing canonical
  `TalosMobileImageInputPart`;
- propagate typed image results through controller and loop without flattening
  them into tool-result text;
- persist only the Vault file/grant/binding identifiers on the assistant
  message, never base64 image bytes in SQLite message metadata;
- use the existing message-attachment renderer after reload;
- resolve message input parts only for user messages. An assistant image is a
  durable visual result, not automatic model context on every future turn.

Rejected alternatives:

- base64 in assistant metadata: rejected for encrypted-row size, duplication,
  reload cost, and lack of a bounded storage contract;
- an image-only chat table: rejected because the existing Vault, grant,
  attachment binding, and renderer already provide the required lifecycle;
- a new provider SDK: rejected because the provider adapters already implement
  the small official REST contracts and this defect is downstream of them;
- relying on the Library tile alone: rejected because the user-visible chat
  result and the model-visible tool result are separate compatibility
  contracts.

## Security and lifecycle constraints

- generated bytes remain untrusted and pass through the existing Vault
  ingestion/hash pipeline before they can be persisted in a message;
- a retained grant is bound to exactly one assistant attachment;
- generated assistant attachments are not replayed automatically to providers
  on later sends;
- a save failure cannot fabricate a durable attachment;
- provider payloads and storage paths never enter message metadata;
- no schema migration is required.
