# Research dossier - OpenRouter and Gemini image generation

Date: 2026-07-28  
Subsystem: TALOS mobile image gateway / provider routing  
Incidents: OpenRouter tool endpoint mismatch; Gemini Imagen 404

## Local diagnosis

- `TalosImageProvider` excluded OpenRouter, although OpenRouter is a configured
  BYOK provider.
- the controller considered only OpenAI and Gemini keys when deciding whether
  to advertise `generate_image`;
- OpenRouter general model discovery defaults to text models, so it cannot
  substitute for the dedicated image catalog;
- Gemini selection matched any id containing `image` and reverse-sorted names,
  which admitted `imagen-*` and could select Imagen Ultra;
- that selected id was then sent to Gemini's `/v1beta/interactions` endpoint,
  producing the observed 404;
- `b64_json` parsing discarded the provider's declared `media_type`.

## Current primary sources

1. OpenRouter, **Image Generation**, inspected 2026-07-28:
   <https://openrouter.ai/docs/guides/overview/multimodal/image-generation>
   - discovery: `GET /api/v1/images/models`;
   - generation: `POST /api/v1/images`;
   - required request fields: `model`, `prompt`;
   - normalized `aspect_ratio`, `output_format`, and bounded `n`;
   - response: `data[].b64_json` plus `media_type`;
   - model entries include architecture, typed parameter descriptors,
     `supports_streaming`, endpoints, and creation time.
2. Google, **Gemini image generation**, inspected 2026-07-28:
   <https://ai.google.dev/gemini-api/docs/image-generation>
   - current REST path: `POST /v1beta/interactions`;
   - current recommended all-round model:
     `gemini-3.1-flash-image`;
   - `response_format.type=image`, supported MIME, aspect ratio, and uppercase
     image size are explicit;
   - Imagen models are deprecated and scheduled for shutdown on 2026-08-17;
     Google recommends Nano Banana/Gemini image models for new work.

Exact upstream pins:

- OpenRouter dedicated Image API contract retrieved 2026-07-28;
- Gemini Interactions image contract retrieved 2026-07-28;
- no SDK dependency is introduced; request/response conformance fixtures pin
  the fields and endpoints in tests.

## Upstream decision

**Adopt the two official REST APIs behind the existing AVM-owned image
gateway.**

- OpenRouter gets its own provider branch, dedicated catalog request, dedicated
  generation endpoint, bearer authentication, and response parser.
- OpenRouter model choice prefers the current chat model's author when that
  author has an image model, then the newest full model reported by the image
  catalog.
- Gemini accepts only `gemini-*image*` models compatible with the Gemini image
  path; `imagen-*`, embedding, edit, and vision-only ids are rejected.
- OpenAI behavior remains unchanged.

Rejected alternatives:

- using OpenRouter chat completions for image-only output: rejected because
  OpenRouter now documents a dedicated Image API and the current chat parser is
  intentionally text/tool-call shaped;
- finding Gemini image capability by a broad `/image/i` name match: rejected by
  the real Imagen endpoint mismatch;
- hardcoding a complete model list: rejected because catalogs change; only the
  documented current fallback floor remains for offline catalog failure;
- integrating a new image SDK: rejected because both providers expose small,
  stable REST contracts and the existing transport already owns timeout,
  endpoint, diagnostics, and redaction behavior.

## Security and cost controls

- keys stay in headers, never URLs;
- exactly one image is requested;
- output is constrained to a chat-compatible raster format;
- provider errors are returned verbatim through the existing redacted
  diagnostics boundary;
- generated bytes remain untrusted and must pass the existing Vault boundary.
